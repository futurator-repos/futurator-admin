Status: review

## Story

As a **developer**,
I want **system-level knowledge articles automatically maintained by the compilation pipeline**,
So that **cross-cutting concerns (pending work, deployment state, tech debt) are always visible as a project dashboard**.

## Acceptance Criteria

1. `knowledge/system/pending-work.md` lists all nodes with maturity < 0.6 or status `flagged`, grouped by phase (discovery, planning, solutioning, implementation, qa, release, support)
2. `knowledge/system/dependency-map.md` shows the top-level import graph across all code articles, derived from `DEPENDS_ON` edges
3. `knowledge/system/debt-registry.md` lists items flagged as tech debt with severity (critical, moderate, low), origin story, and description
4. `knowledge/system/deployment-manifest.md` tracks which code articles are deployed vs. pending deployment, with last deploy date and deploy URL
5. Each system article has valid frontmatter with `type: system` and `phase: system`
6. System articles are fully regenerated on each epic compilation (not incrementally updated)
7. Story-level compilation only updates `dependency-map.md` incrementally (adding new edges, not regenerating)

## Dev Notes

### Architecture Context

System knowledge articles serve as the "dashboard" for the project's knowledge graph. They are cross-cutting synthesis articles that aggregate information from across all other articles. Unlike code or decision articles which are created by specific stories, system articles are regenerated by the compilation pipeline to always reflect the current state.

The four system articles map directly to the `knowledge/system/` directory structure defined in the architecture doc:

```
knowledge/
  system/
    dependency-map.md      ← import graph
    deployment-manifest.md ← deploy state
    debt-registry.md       ← tech debt
    pending-work.md        ← what's next
```

**This story depends on Epic 2 being complete** (story compilation must be working) and on Story 3.1 (epic compilation pipeline must exist for the full regeneration trigger).

### Pending Work Query Pattern

The `pending-work.md` article answers the question "What needs attention?" — this maps to the Cypher query pattern from the architecture doc:

```cypher
-- Pending work — "What's next across the whole project?"
MATCH (n:Node)
WHERE n.projectId = $projectId
  AND n.status IN ['active', 'flagged']
  AND n.maturity < 0.6
RETURN n.nodeId, n.type, n.phase, n.title,
       n.maturity, n.status
ORDER BY
  CASE n.phase
    WHEN 'discovery' THEN 1
    WHEN 'planning' THEN 2
    WHEN 'solutioning' THEN 3
    WHEN 'implementation' THEN 4
    WHEN 'qa' THEN 5
    WHEN 'release' THEN 6
    WHEN 'support' THEN 7
  END ASC,
  n.maturity ASC;
```

### Project Structure Notes

System articles are generated files, not hand-authored. They live on the EC2 instance within each project's `knowledge/system/` directory and are backed up to S3 as part of the regular wiki sync. In Memgraph, they appear as nodes with `type: system` and `phase: system`. The `pending-work.md` article is especially important — it drives "what should I do next?" conversational queries in Epic 5.
