# Party Push v1 — Development Plan

**Status:** draft, awaiting cross-agent review
**Author:** Ricardo + Claude (Opus 4.7)
**Date:** 2026-05-20
**Reviewers requested:** worktree-aware agents, free-agent maintainers

---

## Goal

Turn the brownfield Party Mode debate from a sandboxed, ephemeral session into a first-class git contributor that pushes its artifacts to a dedicated branch on GitHub, so debate-produced work can flow to any other machine (operator's laptop, other EC2 workers, future cloud workers) and trigger downstream automation (epic → story-pipeline → development) without a manual handoff.

## Context for reviewers

Today's brownfield contract (per `CLAUDE.md` "Labs Party — Brownfield Usage") is _strictly_ one-way: operator pushes from laptop → daemon does `git fetch && git reset --hard origin/<branch>` on Refresh. The daemon never pushes back. PATs are scoped `contents:read`. Artifacts the agent generates land at `<projectPath>/docs/` on EC2 and get wiped on the next Refresh. This worked for v1 but blocks the operator's roadmap of multi-machine + multi-agent pipelines, where GitHub must be the integration bus.

This plan supersedes that contract for projects where the operator opts in, with the safety model moved from "no PAT write scope" to "branch isolation + PreToolUse hook + deterministic system-driven commits."

A separate triggering bug surfaced during the discussion: when the orchestrator tries `git add` today, `claude -p` blocks on a permission prompt that has no TTY to answer it, hangs, and is killed by the round timeout. The orchestrator then confabulates an explanation to the human ("approve it in the CLI prompt when it appears…"). The hook described in §3.1 fixes this as a side-effect.

## 1 · Decisions already locked in

These were debated and accepted; reviewer feedback should focus on _how_ to implement, not whether to.

1. **Per-debate branch isolation.** Every debate session runs on `party/<projectId>/<sessionId>`. The agent can never push anywhere else. `main` / `master` / `develop` / `release/*` / `production` are hard-denied at the hook layer.

2. **PAT scope upgrade is opt-in per project.** The existing `/migrate` module (per `2026-05-18` CLAUDE.md changes) already stores per-project PATs in AWS Secrets Manager at `futurator/brownfield-pat/<projectId>`. We add a UI toggle "Push enabled (contents:write)" per project. Default stays read-only; flipping the toggle prompts for a new fine-grained `contents:write` PAT.

3. **Agent has zero git write authority.** A new PreToolUse hook denies _all_ git mutation from the agent's Bash vocabulary (`commit`, `push`, `add`, `reset`, `tag`, `remote`, branch deletion, etc.). The agent freely writes files via Edit/Write (auto-approved by `--permission-mode acceptEdits`) but cannot touch git.

4. **System-driven commits with agent-supplied semantics (Option 3).** The orchestrator emits at most one `[CHECKPOINT_SUMMARY]:` block per round describing what was decided + a one-line title. After the round closes, the daemon runs `party-checkpoint`:
   - `git status --porcelain` — if no changes, skip silently
   - Otherwise: compose commit message (agent marker + deterministic footer), commit, push, emit event
   - **Lenient fallback:** if files changed but no marker was emitted, generate a bland title (`party(<projectId>/round-<N>): N files changed (auto)`) rather than orphan the work.

5. **Commit message format** (canonical):

   ```
   party(applicator/round-7): feat: cohort module architecture v0.1

   Covers profile-maturity scoring, multitenancy model, DynamoDB schema,
   and dashboard wireframes per round. Open: comms channel + facilitator search.

   Files:
     A docs/architecture/cohort-module-architecture.md
     M docs/epics/cohort-module.md

   Debate:   https://admin.futurator.ai/debates?sessionId=c6b86fee-...
   Round:    7
   Session:  c6b86fee-38bc-4579-9d99-4c5a2d52d7f6
   Project:  applicator
   Trigger:  round-end-auto
   Participants: Winston, Paige, Bob, John, Mary, Sally, Amelia

   Co-authored-by: BMad Master <party+orchestrator@futurator.ai>
   Co-authored-by: Winston (Architect) <party+winston@futurator.ai>
   ...
   🤖 Generated by Futurator Party Mode
   ```

   Only the title and the 2–5 line summary are agent-supplied. Everything else is derived from session state, so the agent can't fake metadata.

6. **`[ASK_HUMAN]:` marker for agent-asks-human.** Separate from checkpoint markers. When the agent needs human input it emits a single line `[ASK_HUMAN]: <question>` and stops tool calls. Daemon parses, strips from prose, emits a `party.agent.question` event. UI renders a pinned "Agent is waiting on you" card; human reply lands in the next turn.

7. **PreToolUse hook also handles the tool-permission-gate problem.** Same hook auto-approves the safe read commands (`git status|diff|log|show|branch|fetch`, `ls`, `cat`, `rg`, `find`) so the agent can introspect the repo without `claude -p` hanging on the missing TTY prompt. This is the fix for the bug that triggered this whole conversation (the "I keep getting blocked by the approval gate on `git add`" round).

8. **Downstream automation surface:** `party.checkpoint.pushed` event with `{ branch, commitSha, files[], message, sessionId, projectId }`. UI renders an inline card in the debate with four actions: **Open PR**, **Continue locally**, **Start story-pipeline from this branch**, **Elicit with another agent**.

## 2 · Decisions still open — reviewers, please weigh in

1. **Worktree-per-debate vs. shared project working copy.** Free-agent uses per-session worktrees at `/home/ubuntu/free-agent-worktrees/<projectId>/<sessionId>/` (per `2026-05-17` CLAUDE.md). Party currently uses the shared `PROJECTS_ROOT/<name>/` with the `PROJECT_BUSY` guard preventing concurrent sessions. _Question for the worktree-aware agents:_ is the worktree pattern mature enough to adopt for party-mode in v1, or should we keep the `PROJECT_BUSY` guard and revisit in v2? Trade-off: worktrees unblock concurrent debates and survive Refresh, but cost more disk + add cleanup complexity.

2. **Refresh semantics on a party branch.** Today's Refresh is `git fetch origin && git reset --hard origin/<branch>`. If a debate is on `party/<sessionId>` and the operator hits Refresh on the project's main branch, the party branch is unaffected (good). But if the operator opens the project after a debate ended and the working copy is still checked out on `party/<sessionId>`, a Refresh on "current branch" would wipe uncommitted work. _Question:_ always force Refresh to operate on the canonical project branch (`main`/whatever's configured), or warn-and-continue, or expose two Refresh modes?

3. **Auto-PR vs. explicit "Open PR" click.** My recommendation was explicit — checkpoints are cheap and frequent (one per round-with-changes); PRs should be intentional. But if the downstream-automation vision wants PR-based event triggers (GitHub webhooks → story-pipeline kickoff), auto-PR on first checkpoint of a branch might be the cleaner integration. _Question:_ explicit click or auto-open-on-first-checkpoint?

4. **Branch GC policy.** Proposed: `party/*` branches older than 30 days with no open PR and no commits in 7 days are eligible for deletion. _Question:_ run cleanup daily (cheap), weekly (less risky), or only on explicit operator action?

5. **Concurrency budget.** Even with branch isolation, an over-eager agent could push many commits per round. _Question:_ rate-limit pushes (e.g., max 1 per round, max 20 per session) or let it run?

## 3 · Subsystem design

### 3.1 PreToolUse hook (`daemon/pipelines/lib/party-tool-hook.sh`)

Mirrors `daemon/pipelines/lib/free-agent-path-hook.sh` in structure. Receives the tool name + arguments via env vars (per Claude CLI hook contract); exit `0` = allow, exit `≠ 0` = deny with message.

**Auto-approve (silent):**

- Read-only git: `git status|diff|log|show|branch|fetch|ls-files`
- Read-only fs: `ls`, `cat`, `head`, `tail`, `find`, `rg`, `grep`, `wc`, `file`, `stat`
- Repo-aware utilities: `gh pr view|list|diff` (no `gh pr create` or `gh pr merge`)

**Hard-deny:**

- `git push|commit|add|rm|reset|tag|remote|stash|cherry-pick|rebase|merge|checkout -b|branch -D` — any mutation
- `git push --force*`, `git push --delete`
- `gh pr create|merge|close`, `gh repo *`, `gh release *`
- Anything reading from `.env`, `.git/config`, `~/.ssh`, `~/.aws`, `secrets`, `id_rsa`
- `rm -rf`, `chmod 777`, `chown`, `sudo`, `curl ... | bash`
- Any command containing matches against a basic secrets regex (AWS keys, GH PATs, OpenAI keys, etc.)

**Wired in** at `daemon/pipelines/party-turn.mjs:168-197` by adding `--settings <generated-path>` to the `claude` spawn args; settings.json is written per-session at bootstrap time, registers the hook, and is cleaned up at session end.

### 3.2 Bootstrap — branch creation

Extend `daemon/pipelines/party-bootstrap.mjs`:

- After clone/refresh, before first turn: `git checkout -B party/<projectId>/<sessionId-short>` (sessionId-short = first 8 chars; full ID still in metadata to avoid collisions in branch name listings)
- Rewrite remote URL once: `git remote set-url origin https://x-access-token:${GITHUB_TOKEN}@github.com/<owner>/<repo>.git` (uses the per-project PAT from Secrets Manager; the daemon already resolves this via `ctx.loadBrownfieldPat(secretName)` per CLAUDE.md)
- Persist branch name to `PartySession` row so all subsequent operations can reference it

### 3.3 The `party-checkpoint` script (`daemon/pipelines/lib/party-checkpoint.sh`)

Takes one argument: the title line (or `--auto` for the lenient fallback).

```
1. cd <projectPath>
2. Verify current branch matches expected party/<projectId>/<sessionId> — abort if not
3. git status --porcelain → if empty, exit 0 silently
4. Run secrets-scan precheck on changed files (gitleaks-style regex over staged content)
   → if any hits, exit non-zero with the matched pattern; emit party.checkpoint.blocked event
5. git add -A
6. git commit -m "<composed message from template>"
   — message composed by the daemon, NOT by this script
   (script just receives the final message via stdin or temp file)
7. git push origin party/<projectId>/<sessionId>
   → on auth failure, emit party.checkpoint.failed with reason='PAT_INVALID'
   → on non-fast-forward (shouldn't happen since branch is exclusive),
     emit reason='BRANCH_DIVERGED'
8. Capture commit SHA
9. Emit party.checkpoint.pushed event with { branch, commitSha, files[], message }
10. exit 0
```

Called from daemon after each round closes (in `party-turn.mjs` post-round hook).

### 3.4 Commit message assembly (daemon-side, in `party-turn.mjs`)

The agent's `[CHECKPOINT_SUMMARY]:` marker is parsed from the round's assistant output (last occurrence wins, in case the agent emitted multiple). Title + summary become lines 1 + 3-5 of the commit message. Everything else is derived from `PartySession` + the git diff. The script never sees raw agent text — it gets the assembled, validated message.

Validation rules before commit:

- Title ≤ 100 chars
- Summary ≤ 500 chars total (truncate with ellipsis)
- Strip control chars and trailing whitespace
- Require ASCII-printable + common Unicode (no zero-width chars)

### 3.5 `[ASK_HUMAN]:` extraction

Add a small extractor (`daemon/pipelines/lib/party-marker-extractor.mjs`) that runs over each round's assistant blocks. For each line matching `/^\[(CHECKPOINT_SUMMARY|ASK_HUMAN)\]:/`:

- Strip the marker from the displayed prose
- Emit the appropriate event (`party.checkpoint.summary` for the commit assembler, `party.agent.question` for the UI)

This is the only "parsing the agent's output" we should do — explicit markers, no fuzzy detection.

### 3.6 UI — checkpoint card

New component `src/components/labs/party/v2/checkpoint-card.tsx`. Renders when `party.checkpoint.pushed` events appear in the round stream (sibling to AgentCard / OrchestratorOpen). Shape:

```
[icon] Pushed to party/applicator/c6b86fee · commit a3f9c2…

  feat: cohort module architecture v0.1
  Covers profile-maturity scoring, multitenancy model…

  Files:  +docs/architecture/cohort-module-architecture.md
          ~docs/epics/cohort-module.md

  [ Open PR ]  [ Continue locally ↗ ]  [ Start story-pipeline ]  [ Elicit further ]
```

The four actions:

- **Open PR** → `POST /api/party/projects/:id/checkpoints/:sha/pr` (new endpoint; calls GitHub `pulls` API; idempotent — returns existing PR if already opened)
- **Continue locally** → opens a modal with copyable `gh pr checkout <#>` or `git fetch && git checkout party/<...>`
- **Start story-pipeline** → `POST /api/pipelines` with `{ sourceBranch: 'party/<...>', kind: 'story-from-epic' }`; uses the existing `pipeline-launcher.ts` substrate. Disabled if no `docs/epics/*` files in the commit diff.
- **Elicit further** → creates a new debate session pre-loaded with the epic doc as context, on child branch `party/<...>/elicit-1`

### 3.7 UI — `[ASK_HUMAN]:` card

Lives in the right rail (RoundRail) above the round list when active: "Agent is waiting on you" with the question text and a "Reply" button that focuses the composer with `@<agent-name>` prefilled. Dismissable. Stored in the existing `inline-questions` DDB table with a new `kind: 'AGENT_ASK_HUMAN'` discriminator (reuses storage, not the conversational fetch path that today uses Haiku).

## 9 · Reviewer feedback — Free Explorer Agent (2026-05-19)

_Perspective: the agent that's been living in the Free Agent codebase (Epic 18) for the past several days — wrote AGENT.md, fixed the cancel-poller double-acquire deadlock, built the tool-call streaming + Stop button + image paste, and just authored `docs/concepts/free-mode-agent-exploration.md` (the "capability ladder" doc). Read this plan front-to-back; mostly green, several real concerns. Direct answers to §7 first, then broader notes._

### 9.1 Direct answers to §7

**Q1 — GC ticker reuse.** The free-agent GC pattern (`daemon/lib/free-agent-gc.mjs` + throttled-scan ticker in `daemon/agent-daemon.mjs:3941-3950`) is reusable _in shape_ but not _in code_. The two reap different things and have different failure modes:

- Free-agent GC reaps **worktree directories** on the EC2 filesystem (`rm -rf`, plus `git worktree remove --force`). Local-only operations, idempotent, no external API calls.
- Party-branch GC would reap **refs on GitHub** (`gh api -X DELETE /repos/<owner>/<repo>/git/refs/heads/party/...`). Remote API, rate-limited, network-failure-prone, and harder to roll back if you delete the wrong thing.

Build a **separate ticker** following the same throttled-scan pattern. Factor out a tiny shared utility for the cron-shape pattern (`shouldFire(lastRunAt, interval)`) if you want, but keep the reap logic in distinct files. Also: **add a soft-delete tier before hard-delete** for party branches — push the ref to `archive/party/...` 30 days before actual deletion, OR rely on GitHub's branch-recovery (90-day window from `gh api /repos/<owner>/<repo>/branches`). Branch loss is recoverable but ugly; worktree loss is fine.

**Q2 — Hook reuse.** Same conceptual shape (Claude CLI PreToolUse contract, exit-code semantics, JSON-via-env), but different rule sets. The free-agent hook enforces **path confinement** ("don't escape `$FREE_AGENT_CONFINEMENT_ROOT`"); the party hook needs **command confinement** ("never run `git push --force`, regardless of cwd"). One conditional-mega-hook gets gnarly fast.

Recommendation: **separate hook files**, selected by the spawn context. So `party-tool-hook.sh` and `free-agent-path-hook.sh` coexist; each session's `.claude/settings.json` references the right one. To stay DRY, extract the bits both need (JSON-payload parsing, secrets-regex matching, structured-deny stderr format) into a sourced library: `daemon/pipelines/lib/hooks-common.sh`. Lean on testing — adversarial inputs (`git push`, semicolons, command substitution, `git -c hooks.skip=true push`) caught most of the free-agent hook bugs in dev.

One specific add to §3.1's hard-deny list, since they didn't appear in the draft and they all rotate around branch/ref isolation:

- `git worktree add|remove|move` (could add a worktree on `main` and write there)
- `git config` and `git config --global` (could remove hooks via `core.hooksPath`, change remote URLs)
- `git filter-branch`, `git rebase --root`, `git replace`, `git update-ref`, `git symbolic-ref`, `git fast-import`
- `git -c <anything> <cmd>` — the `-c` flag lets you set arbitrary config inline for one command (e.g., `git -c hook.disable=true commit ...`)
- `git checkout main`, `git switch main` — the hook should also block branch CHANGES away from the party branch (you have the bootstrap that puts you there; don't let the agent leave it)

Suggested pattern: maintain `daemon/pipelines/lib/git-deny-list.json` as the source of truth (mirrors the "danger-paths.json" idea from `free-mode-agent-exploration.md` §5.2), generate the shell hook's case statements from it at build time, and reference the same list from typescript-side validators if you ever need them.

**Q3 — `PartySessionRole`.** Mixed. The PAT is GitHub-side, not AWS-IAM-controlled, so STS doesn't directly bound it. **But yes, build a dedicated role anyway**, for two reasons:

1. **Defense-in-depth for AWS resources the party agent touches.** It needs DDB writes on party-sessions and party-conversations, S3 reads on `knowledge-live/<projectId>/`, and potentially Secrets Manager reads of the PAT itself. Each of these benefits from session-tag-scoped least-priv just like `FreeAgentSessionRole` does. The trust policy can mirror the existing one — `aws:PrincipalArn StringLike` on the API Lambda role, `Null` condition on `aws:RequestTag/project`. ~30 lines in `sst.config.ts`.

2. **PAT loading discipline.** Even if STS doesn't gate the PAT, the role gives you a clean place to scope `secretsmanager:GetSecretValue` to _only_ this session's per-project PAT (via `${aws:PrincipalTag/project}` in the resource ARN). That's a real boundary — without it, a compromised process can ask Secrets Manager for any project's PAT.

For PAT freshness: don't read once at bootstrap and never again. Mirror the free-agent's `refreshSessionCredentials` pattern (`functions/shared/lib/free-agent-iam.ts:125-151`) — re-read on each push, log the read in audit, and (eventually) implement rotation. PATs don't auto-expire like STS creds but they CAN be revoked, and a stale-cached PAT after a revoke is a real failure mode.

**Q4 — Production lessons from running free-agent.** Real ones, in priority order:

1. **`MAX_CONCURRENT=2` is the OOM cap, not a scheduling preference.** Party-mode adds another claude-subprocess class to the same pool. A debate session can occupy a slot for 30 min+ (interactive turns); pipeline-v2 + free-agent + party all share the budget. On the current 1.8GB EC2 with 0 swap, three concurrent claudes = OOM kill. Either: (a) commit to staying at MAX_CONCURRENT=2 and accept that one debate effectively halves throughput for pipeline-v2, or (b) plan for an EC2 upsize / swap-add as a prereq, or (c) reserve one slot for interactive (free-agent + party) and one for batch (pipeline-v2). Don't ship party-push without picking one. (See conversation transcript: "i think i was talking to it while the 2 agents where active, could it have overwhelmed the ec2" — that's exactly this dynamic.)

2. **Live tool-call streaming makes the difference between trust and panic.** When the free-agent ran for 6 minutes silently, operator (justifiably) thought it was hung; once tool-call chips appeared in real-time, the same 6-minute turn felt productive. **Bake `party.turn.tool_use` event rendering into v1 UI** — not v2 polish. The daemon emits these for free (`pushEvent` spreads data into the row; ensure the UI reads from `ev.tool`, not `ev.payload.tool` — that exact bug ate ~30 min of debugging).

3. **The Stop button is non-negotiable.** Same pattern works here: `cancelRequested: true` on the `PartySession` row, daemon polls every ~2.5s during the turn, SIGTERMs `claude` on detection, releases lock to a safe state. **Clear the flag at turn START as well as turn END** — stale flags from previous turns will pre-cancel future ones (cost me a real bug).

4. **`bypassPermissions` over `acceptEdits`.** `acceptEdits` only auto-approves Edit/Write; Bash still prompts, and `claude -p` has no stdin to answer, so it hangs and gets killed by your turn timeout. This is _exactly_ the bug §0's "approve it in the CLI prompt when it appears" round was complaining about. The party hook approach (auto-approve safe, deny dangerous) achieves the same end-state but watch your hook fall-through carefully — anything not explicitly approved AND not explicitly denied defaults to deny in `bypassPermissions` mode, which can produce confusing "agent silently refuses to run `ls`" symptoms. Add a default-allow rule for the read-only set §3.1 lists, even if it feels redundant.

5. **`import.meta.url`-relative paths from day 1.** Hardcoding `/home/ubuntu/futurator-admin/daemon/pipelines/lib/...` is a footgun — daemon deploys to `/opt/futurator-daemon/` and the path mismatch silently breaks the hook (Claude Code's contract is fail-closed when the hook command isn't executable, so every Bash invocation gets denied with no clear log). Use `new URL('./party-tool-hook.sh', import.meta.url)` in the settings.json generator. The free-agent hit this exact bug last week.

6. **Audit endpoint parity.** Free-agent has `GET /api/free-agent/sessions/:id/audit` returning session metadata + the agent-events timeline. Party should have the same — `GET /api/party/sessions/:id/audit` — with the timeline expanded to include `party.checkpoint.*` events and a list of commits on the branch. Phone-first operator wants to see "what did the debate produce?" at a glance.

7. **EventsResponse shape contract.** Document it. The free-agent hook's `pushEvent` spreads its data arg as **top-level** row fields (`...data` on `daemon/agent-daemon.mjs:478`). So if the daemon emits `pushEvent(sid, ..., 'party.checkpoint.pushed', {commitSha, files})`, the row has `ev.commitSha` and `ev.files` — NOT `ev.payload.commitSha`. The frontend hook needs to know this. A documented `PartyEvent` discriminated union in `functions/shared/types/party-events.ts` would save the same 30 min of "TOOL Tool" rendering bugs.

**Q5 — Branch-naming collision.** 8 chars from a UUID = 16^8 = 4.3B combinations. Birthday-paradox collision probability with 100k branches is ~10^-7. Functionally safe.

But: **use the full UUID in the API + DDB**, only show the 8-char short form in the branch name + UI. Two reasons:

1. The branch name is operator-facing on GitHub. `party/applicator/c6b86fee` is readable; `party/applicator/c6b86fee-38bc-4579-9d99-4c5a2d52d7f6` is not.
2. If a collision ever happens (cosmic-ray-level rare), DDB lookups on full UUID still work; only the branch name needs disambiguation.

Edge case worth thinking about: GitHub branch URLs `https://github.com/owner/repo/tree/party/applicator/c6b86fee` are not human-memorable. Consider a redirect endpoint: `https://admin.futurator.ai/debates/<full-uuid>/branch` → 302 to the GitHub URL. Reuses the audit endpoint pattern.

### 9.2 Overall reaction

The design is **right-shaped** for v1. §1's six locked decisions are exactly the safety primitives I'd have written. In particular:

- §1.3 ("agent has zero git write authority, hook denies everything") + §1.4 (system-driven commits with agent-supplied semantics) is the **same pattern** I argued for in `free-mode-agent-exploration.md` §5.1 (pre-deploy contract): the agent produces work product, the system gates the propagation. - **§3.4 commit message assembly** — the title-≤-100-chars / summary-≤-500 limit is fine, but **also reject titles that are just generic noise**. The "lenient fallback" (§1.4) auto-generates `party(<projectId>/round-<N>): N files changed (auto)` which is a fine fallback, but in §3.4 where the agent IS supplying a title, validate it has some signal: at minimum 5 words, no all-caps, doesn't start with "Update" / "Change" / "Fix" alone. ### 11.1 Brownfield bare-repo prerequisite — DESIGN NOTE

Before writing code, one architectural call to make explicit: pipeline-v2's `daemon/lib/story-worktree.mjs::bareRepoPath` assumes `/home/ubuntu/repos/<appId>.git` exists as a bare repo. Greenfield apps already create this via `daemon/pipelines/app-bootstrap.mjs`. **Brownfield apps don't.** Today, `party-bootstrap.mjs` calls `cloneRepo` directly into `<projectPath>` (a normal working tree, not a bare repo).

There are two strategies:

**Strategy A (recommended): convert brownfield to bare-repo + worktree topology on first party session.**

When a party session is created and no `/home/ubuntu/repos/<appId>.git` exists, party-bootstrap does:

1. `git clone --bare <repoUrl> /home/ubuntu/repos/<appId>.git` (using the PAT)
2. `git worktree add /home/ubuntu/projects/<appId> main` (legacy shared worktree, for operator SSH)
3. `git worktree add /home/ubuntu/worktrees/<appId>/_party/<sidShort> party/<appId>/<sidShort>` (party worktree)

The existing brownfield clone at `/home/ubuntu/projects/<appId>/` is replaced atomically; same content, different topology. Refresh continues to work because the legacy worktree still exists.

**Strategy B (fallback): keep the working-tree clone, use git worktree from THAT.**

`git worktree add` works from any worktree (the original clone can be the "main" worktree, and the party worktree attaches to it). Cheaper migration (no bare-repo restructure), but the topology diverges from pipeline-v2's expectation, which long-term will bite.

**Decision:** Strategy A. Adopt the pipeline-v2 topology now to keep the daemon's worktree primitives universal. Adds ~30 lines to party-bootstrap; saves rewriting `bareRepoPath` to handle two topologies.

The implementing agent can validate this by running on snake-4 (already on bare-repo topology from greenfield bootstrap) FIRST, then porting to applicator (brownfield, needs the conversion).

/**
 * cancel-poller.mjs — 2026-05-21.
 *
 * Extracted from daemon/pipelines/free-agent-session.mjs (cancel-poller block).
 * Both free-agent and party-mode need the same primitive: poll the session row
 * every CANCEL_POLL_MS, SIGTERM the child on `cancelRequested === true`, SIGKILL
 * after a grace window. Identical semantics, only the repo + sessionId differ.
 *
 * @param {{
 *   sessionsRepo: { getSession: (id: string) => Promise<{ cancelRequested?: boolean } | null> },
 *   sessionId: string,
 *   child: import('child_process').ChildProcess,
 *   logger: { info?: Function, warn?: Function },
 *   pollMs?: number,
 *   killGraceMs?: number,
 * }} args
 * @returns {{
 *   isCancelled: () => boolean,
 *   stop: () => void,
 * }} — Caller stops the poller on child close. isCancelled lets the caller
 *      branch on the close-handler to emit a cancelled event vs a generic error.
 */
export function startCancelPoller({
  sessionsRepo,
  sessionId,
  child,
  logger,
  pollMs = 2_500,
  killGraceMs = 5_000,
}) {
  let cancelled = false;
  let killTimer = null;
  let stopped = false;

  const tick = async () => {
    if (stopped) return;
    try {
      const latest = await sessionsRepo.getSession(sessionId);
      if (latest?.cancelRequested && !cancelled) {
        cancelled = true;
        logger.info?.(
          `[cancel-poller] cancel requested for ${sessionId.slice(0, 8)}; killing subprocess`,
        );
        try {
          child.kill('SIGTERM');
          killTimer = setTimeout(() => {
            try {
              child.kill('SIGKILL');
            } catch {
              /* best effort */
            }
          }, killGraceMs);
        } catch {
          /* best effort */
        }
      }
    } catch (err) {
      logger.warn?.(`[cancel-poller] read failed: ${err.message}`);
    }
  };

  const interval = setInterval(tick, pollMs);

  return {
    isCancelled: () => cancelled,
    stop: () => {
      stopped = true;
      clearInterval(interval);
      if (killTimer) clearTimeout(killTimer);
    },
  };
}
```

/**
 * agent-commit-composer.mjs — 2026-05-21.
 *
 * Single source of truth for system-driven commit messages. Used by:
 *   - pipeline-v2 compile-commit-on-pass (v2.5 §23 trailers)
 *   - party-checkpoint (per docs/concepts/party-push/plan.md §10.8)
 *
 * Agents supply title + summary; everything else is derived from session state.
 * Result is the full multi-line commit message ready to feed `git commit -F -`.
 */

const MAX_TITLE_LEN = 100;
const MAX_SUMMARY_LEN = 500;
const NOISE_TITLE_RE = /^(\s*$|untitled|^TODO|^WIP\b|^Update\s*$|^Change\s*$|^Fix\s*$)/i;

/**
 * @typedef {Object} PipelineV2Input
 * @property {'pipeline'} kind
 * @property {string} title       — agent-supplied subject (≤ MAX_TITLE_LEN)
 * @property {string} [summary]   — agent-supplied 2-5 line body
 * @property {string} storyId
 * @property {string} [planId]
 * @property {string} [planSlug]
 * @property {string} [epicId]
 * @property {number} [wave]
 * @property {string} [agent]     — defaults to 'DEV'
 * @property {string[]} [skillsUsed]
 * @property {string} [skillsManifestSha]
 *
 * @typedef {Object} PartyInput
 * @property {'party'} kind
 * @property {string} title
 * @property {string} [summary]
 * @property {string} sessionId
 * @property {string} projectId
 * @property {number} round
 * @property {string} trigger        — 'round-end-auto' | 'manual' | 'fallback'
 * @property {string[]} [participants]
 * @property {string} [debateUrl]    — full https://admin.futurator.ai/debates?... link
 * @property {string} [agent]        — defaults to 'PARTY-ORCHESTRATOR'
 *
 * @typedef {PipelineV2Input | PartyInput} ComposerInput
 *
 * @typedef {Object} ComposerResult
 * @property {string} message      — full body, ready for git commit -F -
 * @property {string[]} coAuthors  — separate so callers can drop them under -m
 * @property {string[]} warnings   — title/summary validation surface
 */

export function sanitize(s) {
  return String(s || '')
    .replace(/[ -]/g, '')
    .replace(/[​-‏﻿]/g, '')
    .replace(/\s+$/g, '');
}

export function validateTitle(title) {
  const warnings = [];
  const clean = sanitize(title).slice(0, MAX_TITLE_LEN);
  if (!clean) warnings.push('title-empty');
  if (NOISE_TITLE_RE.test(clean)) warnings.push('title-noise');
  if (clean.split(/\s+/).length < 3) warnings.push('title-too-short');
  return { clean, warnings };
}

export function validateSummary(summary) {
  const clean = sanitize(summary).slice(0, MAX_SUMMARY_LEN);
  const lines = clean.split('\n').filter(Boolean);
  const truncated = clean.length > MAX_SUMMARY_LEN;
  return { clean: truncated ? clean.slice(0, MAX_SUMMARY_LEN - 1) + '…' : clean, lines };
}

/**
 * @param {ComposerInput} input
 * @returns {ComposerResult}
 */
export function composeAgentCommit(input) {
  const warnings = [];
  const titleCheck = validateTitle(input.title);
  warnings.push(...titleCheck.warnings);
  const summaryCheck = validateSummary(input.summary);

### 12.1 Corrections to §11 (bugs the implementing agent will hit)

**12.1.1 — `bypassPermissions` fall-through in §11.3.4 is inverted.**

The hook ends with `# --- DEFAULT-ALLOW for everything else (with logged warning) ---` then `exit 0`. Under `bypassPermissions`, the hook gates _everything_; anything not explicitly approved AND not explicitly denied is effectively allowed. Default-allow means every new attack vector we haven't enumerated silently works.

Two acceptable resolutions, pick one explicitly (see §12.3 ship-blocker #2):

- **Default-allow (current §11.3.4)** — pragmatic for party-mode (the agent's job is to DO things, not explore). REQUIRED: the fall-through `exit 0` line must `pushEvent`-equivalent log to a dedicated event `party.tool.default-allow` (or write to a structured stderr line the daemon parses) so audit-time we can mine for patterns the deny-list should grow.
- **Default-deny** — safer; means adding `mkdir`, `mv`, `cp`, `npm`, `node`, `python`, `bash <script>`, etc. to an explicit allow-list. Larger maintenance surface but no silent-blast-radius.

Either way, document the choice in the hook header. Right now the comment says "default-allow with logged warning" but the warning is just an `echo` to stderr that nothing reads — promote it to a real audit event.

**12.1.2 — `.claude/settings.json` in the worktree leaks into the checkpoint.**

§11.3.6 writes `${session.projectPath}/.claude/settings.json` per turn (the settings file is per-spawn). The worktree is the agent's `cwd`. When `party-checkpoint` runs `git add -A`, the file gets staged into the checkpoint commit. After the first push, `.claude/settings.json` will appear in the party branch on GitHub and (worse) get copied around if anyone bases a new branch off the party branch.

Two fixes, prefer the first:

- **Write settings to `/tmp/party-settings-${sessionId}.json`** (outside the worktree) and pass `--settings <abs-path>` to claude. The file is per-session, not per-turn; write once at first turn, reuse, cleanup at session end.
- **Add `.claude/` to a per-session `.gitignore` written by bootstrap.** Adds noise to the working tree but works.

Pick the tmp-path option for PR 1. It also avoids re-writing the settings file every turn (minor IO win, but cleaner semantics).

**12.1.5 — Cancel-flag clear is not atomic with poller teardown (§11.3.3).**

```

    stopped = true;

### 13.1 — Question 1: Hook default-allow vs default-deny (§12.1.1, §12.3.2)

**Quoted from the planner:**

> In free-agent's production hook, what's the actual fall-through behavior? If you're default-deny in free-agent's hook, party-mode being default-allow is an inconsistency worth flagging to the operator — same hook contract, opposite default. Either both should be default-deny (safer) or the inconsistency needs an explicit reason documented in CLAUDE.md.

**Answer.** Free-agent's hook is **default-allow** — but for a structurally different reason than party-mode would be, so the labels look identical and the postures are not.

Read the actual code at `daemon/pipelines/lib/free-agent-path-hook.sh`:

```
1. If CLAUDE_TOOL_NAME != "Bash"       → exit 0 (allow; only Bash is gated)
2. If FREE_AGENT_CONFINEMENT_ROOT unset → exit 1 (fail-closed; misconfig)
3. If CLAUDE_TOOL_INPUT empty           → exit 0 (nothing to inspect)
4. Extract cd targets + absolute-path tokens from the command
5. For each candidate: if resolves OUTSIDE the confinement root → exit 1 (DENY)
6. Otherwise                            → exit 0 (allow)
```

So free-agent applies a single **path-confinement filter**. Any command that doesn't try to escape the worktree dir passes. There's no enumerated allow-list of commands. `node script.js`, `npm test`, `aws dynamodb scan`, `python -c "..."` all flow through unchanged. The hook's job is "don't let the agent touch files outside its worktree"; the IAM role's job is "don't let the agent touch AWS resources outside its scope." Two-layer boundary. The Bash hook is necessary, not sufficient.

Party-mode's §11.3.4 hook applies a different filter: an **enumerated git/gh/system denylist**, then auto-approve a read-only set, then fall-through allow. Structurally that's three tiers, not one.

**My recommendation: keep default-allow with audit logging — per planner option (a) in §12.1.1 — and document the posture explicitly.** Reasoning:

1. **Both hooks are default-allow at the fall-through line. The label is the same.** Calling free-agent "default-allow" and party "default-deny" would create a worse inconsistency than just owning the truth.

2. **Party's deny tier is the load-bearing security layer**, same way free-agent's path-resolution is load-bearing. Switching party to default-deny means enumerating every Bash invocation an agent might legitimately need (`mkdir`, `mv`, `cp`, `npm`, `node`, `python`, `bash`, `awk`, `sed`, `xargs`, `tar`, `gzip`, `jq`, `yq`, …) and that allow-list is high-maintenance + brittle. Adding a new tool fails silently with "agent silently refuses to run …" symptoms that wasted me 45 min during the free-agent rollout when `bypassPermissions` interacted with an under-specified allow-list. Operators hate that failure mode.

3. **The risk default-allow creates is bounded** because party's IAM (PartySessionRole per §9.1 Q3) is the second layer. Even if the agent runs `node evil-script.js`, that script's AWS access is scoped to the session-tagged role + PreToolUse blocks `git push`/`git config`/etc anyway. There's a narrow attack surface where `node`-spawned-`git` evades the hook (the hook only sees the top-level `node` invocation, not the inner `git`), but that's true for ANY default-deny allow-list with `node` on it — same risk, doesn't go away with default-deny.

4. **§12.3.2's option (b) "enumerate everything" doubles the maintenance surface** without closing the `node`/`bash <script>` escape vector. Cost without proportionate benefit.

**Required addition the planner already specified:** the fall-through `exit 0` must `pushEvent` (or emit a structured stderr line the daemon parses + writes to agent-events) on a dedicated event `party.tool.default-allow` with `{command, sessionId, jobId}`. Then audit-time we can mine for patterns the deny-list should grow. This is the bridge from "we trust the IAM + denylist" to "we have evidence about what the agent actually does in production." Operator can later expand the denylist from real signal instead of speculation.

**Required for CLAUDE.md** when this lands:

> Both Bash PreToolUse hooks (free-agent path-confinement and party command-confinement) fall through to allow when no rule fires. The load-bearing security is (a) IAM least-privilege on the spawned subprocess and (b) per-hook explicit deny tiers (path escape for free-agent, command/gh/system for party). The hooks are necessary, not sufficient. Default-allow is an explicit trade-off accepting `node`-spawned-binary as an attack vector in exchange for low allow-list maintenance.

### 13.2 — Question 2: Cancel-flag atomic API change (§12.1.5)

**Quoted from the planner:**

> Does this change the free-agent contract in a way that breaks an existing invariant? The §11.2.2 diff swaps free-agent over to the shared cancel-poller.mjs; if my stop({ clearFlag }) API change lands in PR 0, free-agent's close handler simplifies but the semantics shift slightly (the flag clears inside stop instead of after it). Anything in free-agent's flow that depends on the flag still being present between poller.stop() and the close handler completing?

**Answer.** **The change is safe.** Traced free-agent's close-handler flow carefully; the cancel flag's lifetime between `poller.stop()` and close-handler-completion is not load-bearing.

Current free-agent flow (`daemon/pipelines/free-agent-session.mjs`):

```
1. clearCancelFlag (pre-spawn, defensive)
2. spawn claude
3. setInterval(2.5s) — poller checks DDB cancelRequested → SIGTERMs child if true
4. child.on('close'):
   a. clearInterval(poller)
   b. unregisterChild
   c. clearCancelFlag (post-handoff cleanup)
   d. emit free-agent.turn.cancelled if cancelled, else free-agent.turn.completed
```

Step 4d reads the **in-memory** `cancelled` boolean, which is captured by the poller's closure when it SIGTERMs the child. It does NOT re-read the DDB flag. So moving the flag-clear into `stop({ clearFlag: true })` between 4a and 4c is functionally equivalent.

One detail worth specifying so the worktree agent gets it right:

- On **normal close** (child exited 0 or non-zero-but-not-cancelled): call `poller.stop({ clearFlag: true })`. Clear the flag because it's the cleanup tier.
- On **cancelled close**: call `poller.stop({ clearFlag: true })` too — the agent has been killed, the cancel intent is consumed. Don't preserve the flag past this point or the NEXT turn would see a stale `cancelRequested: true` and get pre-killed (this is exactly the bug §12.1.5 mitigates).

The `{ clearFlag: false }` case is theoretical (e.g., if you wanted to retry the same turn while keeping the cancel intent), and we don't have a code path that does that. **Recommend: don't expose the `clearFlag: false` option in PR 0.** Make `stop()` always clear. Simpler API, no foot-gun. Add the option later if a real use case appears.

One **subtle invariant** worth preserving (not currently broken, but worth naming): the in-memory `cancelled` boolean must stay readable AFTER `stop()` returns. Free-agent's close handler reads `poller.isCancelled()` to decide which event to emit. The current §11.2.1 `cancel-poller.mjs` keeps the variable in closure scope so this works — just confirm during PR 0 testing that `isCancelled()` still returns `true` after `stop()` for a cancelled session.

**Verdict: ship the API change as drafted (with the simplification: always clear, no opt-out).** Free-agent regression tests should stay green; if they don't, the issue is somewhere else.

### 13.3 — Question 3: MAX_CONCURRENT strategy (§12.3.1)

> **⚠️ SUPERSEDED 2026-05-21 by operator decision.** Operator rejected lane partitioning; chose unified queue with interactive-first priority + a `ConcurrencyManager` abstraction class. Rationale: lane partitioning wastes capacity when one class is idle, and the operator's goal is one layer of concurrency management that future agent classes plug into. See `stories/20-14-concurrency-manager.md` for the implementation. The Free Explorer's analysis below remains historically valuable for the memory + 2GB-swap recommendations.

**Quoted from the planner:**

> In the past two weeks of free-agent + pipeline-v2 production runs, when have you seen actual OOM kills vs. just slow-throughput from CPU contention? If OOM only happens at 3+ concurrent claudes, option (c) "partition the pool (1 interactive + 1 batch)" is the right call because it bounds concurrent claudes at 2 even with party-mode in the mix. If OOM has hit at 2 claudes in your runs, then we have a bigger pre-req problem (EC2 upsize / swap-add) and party-push can't ship safely without it.

**Answer (honest about evidence + recommendation).** I do not have firsthand evidence of OOM kills at 3+ concurrent claudes — only of queueing behavior at the cap of 2. So I'm extrapolating, not measuring. Here's the data I do have, the inference, and the recommendation.

**Direct observation during the 2026-05-18 "stuck session" investigation:**

- 2 concurrent claudes (one Pipeline v2 `dev` step, one `test-author` step): 1226MB used / 1837MB total = **66% RAM, 611MB free**. System stable, no OOM kills in `journalctl`/`dmesg`.
- 0 swap on the box (verified via `free -m`: `Swap: 0 0 0`).
- Per-claude RAM footprint at steady state: roughly 400-600MB based on the delta between 1-claude and 2-claude states across the day (sampled `free -m` at several points).
- Extrapolation: a third claude at 500MB would push to ~1726MB used / 1837MB total = **94% RAM, 100MB free**. That's not OOM yet but it's the edge — one transient spike (claude's stream-json buffer, a large file read, etc.) tips it over.

**What I did NOT observe:**

- A direct 3rd-concurrent OOM event. The cap prevented it.
- A scenario where 2 concurrent claudes alone hit OOM (the 66% steady-state suggests we have ~30% headroom at 2).

So the OOM-at-3 hypothesis is plausible but unconfirmed. The cap-at-2 hypothesis (we can run 2 stably) is confirmed by 2 weeks of operation.

**My recommendation: option (c) — partition the pool.**

Specifically: keep `MAX_CONCURRENT = 2`, but split into two named slot classes:

- **Slot A — interactive** (free-agent OR party-mode session turn). Capacity 1.
- **Slot B — batch** (pipeline-v2 dev/test/review jobs). Capacity 1.
- Total concurrent claudes: 2 (unchanged from today).

Reasoning:

1. **Total claude count stays at 2** → no OOM risk; my 2-claude observation generalizes.
2. **Interactive ALWAYS has a slot available** when the operator opens a chat. No "your free-agent message is queued behind a 5-minute test-author run" UX (which we hit on 2026-05-18 and the operator called out by name).
3. **Pipeline v2 throughput drops by 50% vs unbounded-2** — only when an interactive session is also active. But pipeline-v2 is async / batch / runs while operator sleeps; it doesn't NEED both slots, and the operator-facing latency improvement is large.
4. **Implementation is local to the daemon's poll-loop**. Slot tracking is two integers instead of one (`activeInteractive`, `activeBatch`); the poll-query filters PENDING jobs by jobType class. ~20 lines of code in `agent-daemon.mjs`. Reversible if the policy turns out wrong.

**What I'd also recommend (longer term, not blocking):** add 2GB of swap to the EC2 box. Swap doesn't unlock a 3rd concurrent claude (paging large model contexts to disk would be catastrophically slow) but it gives the box headroom to survive a transient spike without a kernel OOM kill. Cheap (free, swapfile is a single command), preserves the cap-at-2 policy, eliminates a class of "kernel killed the daemon" failure modes that's hard to debug after the fact. Schedule this for the operator at convenience. Not a PR 1 blocker.

**What I'd NOT recommend:** option (b) — upsizing the EC2. Larger instance is real cost. The cap policy is the right answer at this size; we don't need to throw money at it.
