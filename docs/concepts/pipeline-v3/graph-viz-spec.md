# Futurator Knowledge-Graph — Visualization Spec (for a UI/UX tool)

**Purpose:** a self-contained brief a designer or a UI/UX generation tool can build the graph visualization from — the data model, the full node/edge catalog, the colour + encoding system, search/filters, the analytics & integrity panels, the interaction model, and the new document↔code layer. No codebase knowledge required.

**Date:** 2026-06-16 · **System:** "Mycelium" / graphify — a Memgraph-backed knowledge graph that models **code ↔ infrastructure ↔ external services ↔ API ↔ documents ↔ cross-project contracts** and their relationships. Today it renders in an admin "Knowledge Graph" tab with a force-directed view; this spec is the basis for the next-generation viz.

- §1 — what data the viz consumes (JSON files + shapes + where they live).

## 1. Data the visualization consumes

The viz is **read-only over static JSON snapshots** (per project), regenerated by the daemon on each sync. Today they live in S3 and are fetched with `cache:'no-store'` + a timestamp param.

**Base URL:** `https://futurator-ai-website.s3.us-east-1.amazonaws.com/knowledge-live/<projectId>/_graph/`

| File                          | Contents                                                                      | Drives                                  |
| ----------------------------- | ----------------------------------------------------------------------------- | --------------------------------------- |
| `graph-snapshot.json`         | `{ projectId, generatedAt, nodeCount, edgeCount, nodes[], edges[] }`          | the graph canvas                        |
| `insights.json`               | centrality, communities, surprising connections, per-node metrics             | God-nodes / Communities / X-ray overlay |
| `orphans.json`                | degree-0 nodes + hard-fail set + status pass/fail                             | Integrity tripwire panel                |
| `dead-code.json`              | files whose only edge is containment                                          | Dead-code advisory panel                |
| `capability-gaps.json`        | components touching shared contracts with no capability tag (`--global` only) | Capability-gap panel                    |
| `<doc>.sections.json` _(new)_ | per-document section manifest (id/title/line range/hash)                      | document/docSection ingestion           |
| `mcp-telemetry.jsonl`         | per-tool-invocation adoption/cost records                                     | (analytics, not the canvas)             |

**Node object (in `graph-snapshot.json`):**

```jsonc
{
  "nodeId": "code/src--components--auth.tsx",
  "kind": "file",
  "label": "auth.tsx",
  "title": "Auth component",
  "summary": "…",
  "projectId": "dino-runner-1",
  "status": "active", // 'active' | 'pruned' (pruned excluded from integrity)
  "updated": "2026-06-16T…",
  // kind-specific (present only where relevant):
  "fields": "…",
  "primaryIndex": "…", // table
  "method": "POST",
  "path": "/plans/:id",
  "auth": true, // endpoint
  "schedule": "rate(1 day)",
  "handler": "…", // cron/lambda
  "billable": true,
  "costUnit": "token", // externalService
  "centrality": 0.42,
  "community": 3,
} // set by analytics (may be null)
```

**Edge object:**

```jsonc
{ "source": "<nodeId>", "target": "<nodeId>", "type": "READS", "provenance": "EXTRACTED" } // 'EXTRACTED' | 'INFERRED' | 'AMBIGUOUS' (default EXTRACTED)
```

## 2. The layered mental model (use this for layout & legend grouping)

Every node belongs to one of **seven layers**. Cross-layer edges are _the whole point_ — they answer "if I touch this code, what infra / paid API / endpoint / document does it reach?" A great viz should make the layers visually distinct (hue family + optional lane/hull) and make cross-layer edges legible.

| #   | Layer                    | Node kinds                                                                | Hue family                      |
| --- | ------------------------ | ------------------------------------------------------------------------- | ------------------------------- |
| 1   | **Code**                 | file, function, class, dir                                                | cool blue / cyan / purple       |
| 2   | **Knowledge (wiki)**     | decision, system, requirement                                             | pink / orange / green           |
| 3   | **Infrastructure**       | table, lambda, cron, secret, bucket, bucketPath, iamRole, cloudfront, vpc | teal / emerald                  |
| 4   | **Events (async)**       | topic, queue, bus, eventSource                                            | violet                          |
| 5   | **API surface**          | endpoint                                                                  | sky                             |
| 6   | **External services**    | externalService                                                           | red/rose (billable = attention) |
| 7   | **Cross-project / Docs** | capability, service, contractRevision, **document, docSection**           | gold / amber + neutral          |

## 5. Visual encoding system

- **Node colour** = kind (the §3 palette). When the **X-ray overlay** is ON, colour switches to **community** (Okabe–Ito 8-colour palette below) and size encodes centrality.
- **Node size** = base-by-kind; under overlay = centrality-scaled; search matches ×2.2.
- **Node shape** = circle (current). _Optional enhancement:_ a per-layer shape (e.g. rounded-rect for infra, diamond for endpoints, document glyph for docs) would aid layer legibility.
- **Edge colour** = type (§4). **Arrows** directed, head at 95%.
- **Provenance styling** _(recommended):_ `EXTRACTED` solid · `INFERRED` dashed · `AMBIGUOUS` dotted + muted — so the operator can trust-weight at a glance.
- **Status:** `pruned` nodes are excluded from integrity; if shown at all, render ghosted.
- **Search dimming:** non-matching nodes/edges fade to `rgba(100,116,139,0.12)`; matches keep full colour + ×2.2 size; direct neighbours stay lit.
- **Billable external services:** add a `$` ring/glyph (cost awareness is a first-class need).

**Community palette (Okabe–Ito, colour-blind safe) — [fixed]:**
`#0072B2` `#E69F00` `#009E73` `#CC79A7` `#56B4E9` `#D55E00` `#F0E442` `#999999` (cycle by `id % 8`).

**Semantic theme tokens (for panels/badges, light/dark):** success `#059669`/`#22c55e`, warning `#b45309`/`#d1a54f`, accent-blue `#4a6b92`/`#7893b8`, accent-purple `#7c3aed`/`#a78bfa`.

## 6. Search & filters

**Free-text + structured query** (single input; space-separated terms AND-ed):

- plain text → fuzzy match on id/title/summary
- `kind:file` · `type:READS` · `status:active` · `phase:…` · `tag:foo` · `id:…` · `title:…`
- e.g. `kind:endpoint auth:false` → public routes; `kind:table` → all DynamoDB tables.

Result: matched nodes highlighted (×2.2) + their neighbours lit; everything else dimmed; a match-count badge + clear button.

**Toggle filters:**

- **Node-kind toggles** — one chip per kind present (with its colour dot + count); hiding a kind also hides its incident edges. (Drive these off the §3 layers — e.g. "hide all infra.")
- **Edge-type toggles** — one chip per edge type present; hide/show by type.
- **X-ray overlay toggle** — size=centrality, colour=community.
- _(new)_ **`includeDocs` overlay toggle** — default OFF; ON draws document/docSection nodes + their doc↔doc↔code edges over the code graph.

**Project picker** — load any `projectId`; persisted in the URL; quick-picks for recent projects. (Multi-project / `--global` federated view shows `service/*` roots + shared `contract/*` nodes + `CONSUMES_CONTRACT` edges.)

## 7. Analytics panels (from `insights.json`)

- **God-nodes** — top betweenness-centrality nodes (the structural load-bearers). Ranked list with score; click → select+focus in graph. Drives the overlay's size scale.
- **Communities** — Louvain clusters; a legend of `#id (n nodes)` swatches in the community palette; overlay colours nodes by community.
- **Surprising connections** — high-centrality edges that _cross_ community boundaries (non-obvious couplings): `source [community dot] ─type→ target [community dot]`, ranked by summed centrality (top 25). Click either endpoint → select.
- **Coverage** — `filesWithArticle / files (pct%)` badge (green ≥70%, else amber).
- **Graceful degrade:** if `mageAvailable:false`, render these disabled/empty (the analytics engine wasn't available) — never an error.

## 8. Integrity panels — two _different_ signals, do not conflate

- **Orphans (hard-fail tripwire)** — degree-0 nodes of a "real" kind (`function/class/table/lambda/endpoint/externalService`) mean an extractor dropped an edge → a **bug**, render **red**, with a pass/fail status badge. (`file`/`dir`/`docSection`/`document` are _soft_ — see below.)
- **Dead code (advisory)** — a _file_ whose only edge is containment (nothing imports/calls it, it defines nothing called) → a **yellow**, non-blocking finding for human review. Distinct query from orphans.
- **Capability gaps** (`--global`) — components touching a shared contract with no capability tag → amber list (the cross-project seam that would silently drift).
- **Unconnected nodes** — degree-0 with a human reason (`detached-function`, `article-unlinked`, `unreferenced-file`, `unreferenced`); click → select.
- _(new)_ **Unlinked sections** — `docSection` with no `REFERENCES`/`GOVERNS` edge → a **warning bucket** (soft-orphan, exit 0), not a hard fail (a narrative section with no code impact is legitimate).

Each list item is **click-through** → selects/focuses the node in the canvas.

## 9. The Document ↔ Code layer (new — the headline feature)

This is what makes the generated **PRD / UX / Architecture** documents _connected and visible_ — to each other and to the code they govern.

- **Nodes:** `document` (`#eab308`, one per prd/ux/arch) + `docSection` (`#f59e0b`, one per manifest section).
- **Edges:** `DERIVED_FROM` (PRD→UX→Arch lineage), `REFERENCES` (story→section), `GOVERNS`/`DESCRIBES` (section→the code/infra it specifies), `SPECIFIES` (doc→plan/epic/story).
- **"Concept docs" panel** — an accordion per document type (PRD / UX / Architecture); UX hidden for non-UI plans. Expanding a section highlights its `GOVERNS`/`DESCRIBES` edges in the graph.
- **doc↔code overlay** (`includeDocs`, default OFF) — overlays the document nodes + their edges onto the code graph; OFF = the code graph is unchanged.
- **Code-node inspector** — when a file/function is selected with the overlay ON, show "**Governed by §X of <docType>**" with click-through to the section.
- **Determinism:** ingested only on document-approval / at the gate (never mid-draft); same docs in → same graph out.

**Why it matters for the viz:** the operator should be able to (a) pick a code node and see which spec sections govern it, (b) pick a spec section and see the code it governs + its lineage back to the PRD, (c) spot unlinked sections (spec with no implementation) and ungoverned code (implementation with no spec).

## 11. Design guidance for "the amazing viz" (what we actually need)

1. **Make the 7 layers readable** — hue family per layer (§2/§3), optional lanes or convex hulls per community, optional per-layer node shapes. The story is _cross-layer reach_, so cross-layer edges must be the most legible thing on screen.
2. **Blast-radius mode** — select a node (or a set of "files I'm about to edit") and highlight everything reachable in ≤2 hops via `READS/USES/CALLS/WRITES/ROUTES/CALLS_ENDPOINT/CALLS_SERVICE/TRIGGERS/SUBSCRIBES/EMITS/IMPORTS`, grouped by layer, with a **"touches a paid API"** flag. This is the single highest-value interaction.
3. **Trust-weighting** — provenance styling (solid/dashed/dotted) so EXTRACTED vs INFERRED vs AMBIGUOUS is visible; let users filter to "EXTRACTED only."
4. **God-nodes & communities** as first-class overlays (size=centrality, colour=community, hulls for clusters), with the surprising-connections list as "architecture smells."
5. **Integrity at a glance** — a red badge if the orphan tripwire failed; yellow buckets for dead-code + unlinked-sections; never block the view, just flag.
6. **Doc↔code as a toggleable overlay** — the code graph stays clean by default; flip `includeDocs` to see specs draped over the code they govern, with click-through both directions.
7. **Cost lens** — billable `externalService` nodes emphasized; a "what does this touch that costs money?" filter.
8. **Performance** — graphs can reach thousands of nodes; support level-of-detail (collapse functions into their file until zoomed in), kind/layer filtering, and search-focus to keep it usable.
9. **Time** — `contractRevision` nodes + `updated` timestamps enable an optional "what changed since commit X" diff view.

## 12. Current baseline & appendix

**Current renderer:** `react-force-graph-2d` (force-directed, canvas, dynamic-import no-SSR) in an admin "Knowledge Graph" tab. It already does: kind/edge colouring (code+wiki kinds only), kind/edge toggles, free-text+structured search with dim/pop, the X-ray overlay, and the god-nodes/communities/surprising-connections/dead-code/orphans/capability-gap/coverage panels. **Gaps the new viz should close:** colours for the infra/event/service/capability/**document** kinds (this spec's §3/§4 palette), the doc↔code overlay, blast-radius mode, provenance styling, and stronger layer legibility.

**Appendix — `insights.json` shape:**

```jsonc
{ "projectId","generatedAt","mageAvailable","centralityAvailable","communityAvailable","threshold",
  "godNodes":[{ "id","kind","title","centrality" }],
  "communities":[{ "community","count" }],
  "surprisingConnections":[{ "source","sourceTitle","type","target","targetTitle","sourceCommunity","targetCommunity","score" }],
  "nodeMetrics":{ "<nodeId>":{ "centrality","community" } } }
```

**`orphans.json`:** `{ projectId, generatedAt, status:'pass'|'fail', orphanCount, hardFailCount, byKind, orphans:[{id,kind}], hardFail:[{id,kind}] }`
**`dead-code.json`:** `{ projectId, generatedAt, count, candidates:[{id,updated,title}] }`
**`capability-gaps.json`:** `{ projectId, generatedAt, gapCount, gaps:[{nodeId,title,contractTouches}] }`

**Agent query surface (for reference — the graph is also queried programmatically via 7 MCP tools):** `query_graph`, `get_node`, `neighbors`, `blast_radius`, `god_nodes`, `orphans`, `shortest_path`. A viz "explain this path" feature could surface `shortest_path` (e.g. component → endpoint → lambda → table).
